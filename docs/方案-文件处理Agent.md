# 文件处理 Agent — 方案（v2，模板改为占位符）

## 1. 定位

「模板驱动 + 证据约束」的文档生成 Agent：
用户上传参考文件 → Agent 按占位符逐项取值 → 有依据的自动填、无依据的明确追问 → 导出成稿。
**不是让模型写文档，是让模型做填空题，且每一空都必须有出处。**

## 2. 模板约定（GitLab 模板必须遵守）

模板用 `{占位符}` 标注待填位置，不再依赖空白表格的形状。

| 写法 | 含义 | 示例 |
|---|---|---|
| `{项目名称}` | 单值占位符 | 直接取该字段 |
| `{{项目名称}}` | 同上（docxtpl 风格，两者都兼容） | — |
| `{活动1名称}` | **集合型**：第 1 条活动的「名称」属性 | 自动对齐到接口协议 excel 第 1 行 |
| `{成员2部门}` | 集合型：第 2 位成员的部门 | 对齐成员清单第 2 行 |

三条规则：
1. **同名占位符全局同值**。模板里写 3 次 `{项目名称}`，三处填同一个值。
2. **集合型序号从 1 开始**，格式为 `{集合名 + 序号 + 属性}`。集合名要和数据源的表名/表头对得上（如「活动」对「网络安全活动」表）。
3. **属性词走同义词桥接**，模板里写「交付物」，excel 里写 `Work Product / 工作产物 / 工作成果` 都能对上。

集合型只写 1 行就够了，**行数由数据条数自动决定**（见 2.1），不必在模板里预留固定行数。

### 2.1 动态扩行

模板里写几行不代表最后就有几行。引擎按数据源条数把表格行调成一致：

| 情况 | 处理 |
|---|---|
| 数据 5 条、模板 4 行 | 复制第 4 行 1 次，占位符序号改写成 5，填第 5 条 |
| 数据 4 人、模板 6 行 | 删掉第 5、6 行，不留一串「待补充」 |
| 没上传对应的表（拿不到条数） | **保持模板原样**，不猜、不缩 |
| 超过 50 条 | 截断到 50 行，避免一份长 excel 把文档撑爆 |

复制的是**占位符最全的那一行**，不是最后一行——模板里偶尔有某行漏写占位符，复制它会静默少一列值。
带纵向合并 / 横向跨列的行不复制也不删除，宁可少填也不搞乱版式。

> 若遇到没有占位符的老模板，引擎会自动回落到「结构推断」模式（表头 + 空白单元格推断），
> 但精度明显低于占位符模式，只作为兼容兜底。结构推断模式不支持扩行：
> 新行是空格子，没有占位符可以替换，值无处落地。

## 3. 四级取值链（核心机制）

每个字段独立走这条链，命中即停：

| 级别 | 做法 | 性质 | 典型场景 |
|---|---|---|---|
| **① 结构化对齐** | `{活动1名称}` → excel 第 1 行「活动名称」列 | 确定性，1.0 | 成员清单、接口协议活动表 |
| **② 规则精确抽取** | 字段名完整出现且后面真的带出值 → 原样取值 | 确定性正则 | 项目名称、文件编号 |
| **③ 模型语义对齐** | 前两级没拿到的字段交给 DeepSeek，整篇读资料找依据 | 模型，**必须过校验** | 模板写「交付物」、资料写 `Work Product` |
| **④ 追问用户** | 前三级都没有 → 生成具体追问，不猜不补 | — | 网络安全负责人、活动开始时间 |

结构化对齐优先的原因：plan.md 里接口协议是 excel、活动一行一条，这类数据只要认出
「集合 + 序号 + 属性」就能 100% 命中，比任何模糊匹配都可靠。
`Target Date` 也会借此预填到「结束时间」——正是 plan.md 要求的预填充。

### 3.1 为什么不做 RAG

RAG 的召回环节本身就是假阳性来源：「网络安全接口人」和「网络安全接口协议」
共享大半词汇，BM25 会把后者排进 Top-K，看起来"检索到了"，实际是两个不同的东西。
更糟的是召回有 K 值上限——正确片段排在 K 名之外就永久丢失，且**没有任何报错**。

所以这里没有向量库、没有 BM25、没有 Top-K：

| 维度 | BM25 召回 | 本项目做法 |
|---|---|---|
| 规则层 | 粗排 + 精判，粗排会丢片段 | 全量扫描，召回率 100% |
| 模型层 | 只喂 Top-K 片段，漏了就再无补救 | **整篇分批送**，模型看到的是全部资料 |
| 误判来源 | 粗排噪音 + 判定规则 | 仅判定规则 + 模型输出校验，都可逐条核对 |
| 依赖 | jieba + rank-bm25 + numpy | 无（标准库 re + httpx） |

③ 是"整篇阅读"而不是"检索增强"：字段少、资料可控（几万字以内），
按 12000 字分批把全文交给模型，而不是先粗排再喂片段。这样"正确片段被挤掉"这个问题根本不存在。

## 4. 接了模型，但没让模型"作答"

这是本项目最关键的设计取舍。模型能解决字面不匹配（模板写「活动名称」、资料写「阶段任务」），
但也最容易顺手编内容。所以模型在这里的职责被压缩到一件事：

> **指出哪一段原文里的哪几个字，对应这个字段。**

它的输出**不直接进正文**，必须先过三道代码校验（`aligner._verify`）：

| 关卡 | 校验什么 | 拦住什么 |
|---|---|---|
| 1 | 引用的资料块必须真实存在 | 模型编一个 `chunk_id` |
| 2 | 引用的原文必须逐字出现在该块里 | 模型把两句话拼成"原文"、把"计划"写成"已完成" |
| 3 | 取值必须能在该块原文中找到出处 | 引文是真的、取值是另外编的（最隐蔽的一种） |

第 3 关按字段类型分别判定：日期允许换格式（`2026/5/30` → `2026-05-30`），
短文本要求字面可溯源，短清单要求**逐项**都能对上，长段落允许压缩归纳但要求内容主体来自原文。
任一条不过 → 退回「需补充」，并把模型说明写进追问让用户补，**绝不放行**。

通过校验的结果标记为**「待确认」而不是「已填」**：模型给的是候选值，核对权在用户。

另外两处防幻觉设计：

- **缓存按「字段 + 语料」指纹存储**，同一份资料重跑结果一致，不会每次给出不同的值
- **模型调用失败一律降级**为规则模式，不让一次网络抖动搞坏整个任务

## 5. 技术栈

| 层 | 选型 |
|---|---|
| 前端 | 原生 JS 单页 + 静态托管（后续可换 React） |
| 后端 | Python 3.13 + FastAPI |
| 模板 | python-docx 解析与占位符替换 |
| 解析 | python-docx / pdfplumber / openpyxl / python-pptx |
| 规则判定 | 结构化表格对齐 + 全量精确匹配（标准库 re） |
| 语义对齐 | DeepSeek（OpenAI 兼容，可换通义/内网模型），httpx 直连 |
| 模型输出防护 | 三道代码校验 + 逐字段缓存 |
| 存储 | JSON 报告（M3 迁 SQLite） |
| 部署 | Docker + docker-compose |

## 6. 界面

1. **任务页**：选模板 → 拖入参考文件 → 填写需求
2. **审阅页**：字段按「需补充 / 待确认 / 已自动生成」三组排列，每项可展开原文依据
3. **缺口追问**：逐条给出具体缺失内容，用户填答后重新判定（已填项不丢）
4. **导出**：保留模板格式，文末附「附录 A 依据索引」+「附录 B 待补充事项」

## 7. 九类文档落地（对应 plan.md）

| 文档 | 输入 | 特殊交互 |
|---|---|---|
| 网络安全接口协议 | 协商结果 / 参考资料 | 直填 |
| **网络安全计划** | 成员清单 xlsx、接口协议 xlsx | **成员勾选 → 活动勾选 → 定义起止时间 → 生成定时提醒** |
| 网络安全概念 | 立项文件、TARA 输入 | 直填 |
| **事件响应计划** | 成员清单 xlsx | **成员勾选** |
| 网络安全档案 | 工作空间文件 | 直填 |
| 网络安全评估 | 工作空间文件 | 直填 |

「网络安全计划」的四步交互是重点，当前引擎已能自动提炼候选（成员 4 人、活动 5 条），
下一步在审阅页把「全部填上」改成「列出候选 + 用户勾选」：
- 成员：列出成员清单全部人员，勾选哪些承担网络安全角色
- 活动：列出接口协议全部活动（含 Work Product），勾选本项目要执行的
- 时间：已勾选活动按 Target Date 预填结束时间，用户补开始时间
- 提醒：时间确定后写入定时任务表，同步到定时任务界面
